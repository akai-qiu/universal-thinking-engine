# 一、定义

在动手拆解之前，先确认"真正要解决的问题是什么"。用户提出的往往是手段（"我要建一个数据库"），需要追问到目标（"我要让用户能查到历史记录"），手段才有优化空间。

# 二、核心原理

如果一开始就把问题理解错了，后面所有系统化工作都是在高效率地解决错误的问题——这是全流程损失最大、也最隐蔽的错误。问题定义排在正向建设之前。

# 三、解决什么问题

接错需求、解决了表层症状而非根因、目标树长歪了还不自知。

# 四、适用场景

一切任务的入口。M/L 级必做；S 级做一次快速复述即可。

# 五、不适用场景

- 用户已经给出精确、经过验证的问题定义时（直接复述确认即可，不要为了流程重问一遍）

# 六、使用方法

1. 复述：用自己的话重述目标与关键约束，暴露理解偏差
2. 追问：你真正要解决的是什么？这个方案失败时最不能接受的后果是什么？
3. 验证：问题背后的价值是什么？有没有更便宜的路径到达同一价值？
4. 列出硬约束（不可协商）与软约束（可权衡）——混在一起是方案反复返工的根源
5. 把确认后的问题定义写给用户过目，再开始拆解

# 九、常见误区

- 把用户的第一句话当问题定义——那是问题陈述，常常连问题都不是
- 不好意思追问，怕显得没听懂——追问恰恰是专业的表现
