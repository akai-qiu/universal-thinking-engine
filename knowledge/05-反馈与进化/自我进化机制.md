# 一、定义

让系统从每次任务中变好的运行机制：知识从产生到发布的完整生命周期管理，加上系统级的自我审查与改进循环。

# 二、核心原理

知识的产生、验证、发布必须是三个独立环节——未经证实的想法直接进入正式知识库，会让知识库逐渐堆满错误经验和重复内容，反而降低判断质量。通过状态机（Draft → Experimental → Pending Review → Validated / Deprecated）和审批权分离（AI 提议、用户审批）实现质量控制。

# 三、解决什么问题

经验只存在于单次对话中随会话消失；错误经验污染知识库；AI 未经约束地自我修改导致系统漂移。

# 四、适用场景

每次 M/L 级任务结束后的沉淀判断；知识条目被证伪时的降级处理；系统级复盘（案例库 ≥5 条后）。

# 五、不适用场景

S 级任务不触发沉淀判断（无可沉淀的方法论增量）；用户明确要求"只处理不沉淀"时跳过。

# 六、使用方法

1. 任务结束后问：产生了"触发条件 + 动作"级别的规则吗？失败案例与成功案例同样有价值
2. 新方法/新规则 → `knowledge/07-实验库/`（experimental）；真实应用记录 → `06-案例库/`；个人偏好 → `memory/`；系统级学习 → `evolution/`
3. 满足五问晋级标准（真实验证/重复性/适用边界/反例审查/增量价值）后送审 `08-待审核知识/`，用户批准后进入正式库
4. 被取代或证伪 → `09-废弃知识/`，保留失败轨迹
5. 每次状态变更登记 `evolution/版本变更日志.md`

运行细则见 `system/protocols/knowledge-lifecycle.md`。

# 七、相关工具

知识状态机、晋级五问、三级权限（自主/提议/审批）、AAR 四问、学习日志。

# 九、常见误区

- 把"两次成功"当有效证明——那只是晋级候选资格，不是有效性证明
- 追求条目数量增长——知识库的价值在于每条都被真实引用过
- 只记录成功案例——失败案例往往更有学习价值
