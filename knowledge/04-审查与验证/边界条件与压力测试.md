# 一、定义

把系统推到极端输入下检验行为：用户量 10 倍、预算砍半、关键人离开、上游断供。目的不是为每种极端做预案，而是知道方案在哪里会断裂。

# 二、核心原理

正常输入下的测试只能验证平均行为；系统的真实鲁棒性藏在边界之外。断裂点的位置决定风险等级：断裂在可恢复的软环节是波折，断裂在不可逆的硬环节是灾难。

# 三、解决什么问题

平均情况设计的系统在极端情况崩溃；方案对外部依赖的脆弱性不透明；容量与冗余规划凭感觉。

# 四、适用场景

- L 级系统上线前
- 依赖外部资源（供应商、平台、关键人）的方案
- 金融/容量/排期等量化规划

# 五、不适用场景

- 边界场景发生概率极低且后果可恢复——过度设防是资源浪费
- 探索原型阶段——先验证核心价值再加固边界

# 六、使用方法

1. 列出关键输入变量与外部依赖
2. 对每个变量做 10× / 0.1× 推演：系统在哪断裂？断裂可恢复吗？
3. 区分软断裂（可恢复，记录监控信号即可）与硬断裂（不可逆，必须设防线）
4. 对硬断裂设冗余或熔断：退路不依赖与主路径相同的资源

# 七、相关工具

极端值推演、故障树分析（FTA）、熔断机制、冗余设计。

# 九、常见误区

- 给所有边界都做预案——按"硬/软断裂"分级，只对硬断裂设防
- 冗余依赖同一资源（主备都在同一个机房/同一个供应商/同一个关键人手里）——假冗余
