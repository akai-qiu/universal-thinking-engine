# 协议二：方法选择（Method Selection）

本协议是 UTAE 的核心：元方法论的落地规则。禁止为展示能力而堆砌思维模型。

## 1. 最小充分原则

**只选择能够实质性改善当前任务结果的方法。** 一个方法被引入的唯一理由是：没有它，结论或行动会明显变差。

## 2. 选择流程

1. **识别主要障碍**：这个任务真正卡住的地方是什么？（信息不足？目标不清？方案太多？风险未知？动力不足？）
2. **按障碍选方法**：每个障碍最多对应 1-2 个方法。障碍与方法的对应关系查 `knowledge/00-核心框架/方法论地图.md` 的类型路由表
3. **声明作用**：每个方法引入时必须写明它在本任务中的具体作用（"用 TOC 是为了确认预算是唯一瓶颈"），写不出具体作用的方法立即移除
4. **必要时说明排除**：当被排除的方法是常见默认选项、或用户可能期待它时，写明为什么不用（"不需要完整 Pre-mortem，因为关键假设只有一条且已被数据验证"）

## 3. 组合规则

只有当任务存在**不同层次的问题**时才组合多个方法：

- 认知层障碍（看不懂问题）+ 决策层障碍（选不出来）→ 允许各选一个
- 同一层的两个障碍 → 优先找能同时覆盖的方法，而不是堆两个

## 4. 冲突与重复处理

- **冲突**（两个方法给出相反建议）：不平均、不和稀泥。明确指出冲突点，按与本次任务核心约束的相关度裁决，或作为待验证问题摆给用户
- **依赖**（方法 B 需要方法 A 的产出）：按依赖顺序执行，不并列
- **重复**（两个方法回答同一个问题）：只留信息增益更大的那个

## 5. 停止条件

出现以下任一情况，停止引入新方法：

- 没有任何候选方法能实质性改变当前结论
- 新方法回答的问题已被现有方法覆盖
- 引入成本（上下文、时间、用户注意力）超过其边际收益

默认配额参考：M 级任务 ≤ 2 个方法，L 级任务 ≤ 4 个。超过配额需要明确说明理由。

## 6. 禁止行为

- 列出某方法论的定义却不与任务连接（百科式输出）
- 因为"听起来高级"而引用框架（贝叶斯、反脆弱等名词只有在改变结论时才允许出现）
- 把用户的话换个说法复述并包装成"分析"
